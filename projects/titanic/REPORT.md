## 모델 선정과 평가

원본과 동일한 `test_size=0.2, random_state=42`로 테스트 20,000행을 고정했습니다.
나머지 80,000행에서 훈련 60,000 / 검증 20,000으로 나누었습니다(검증 seed=43, 계층 분할).
5개 후보의 검증 정확도를 비교한 뒤 최고 후보를 80,000행으로 다시 학습했습니다.
최종 테스트 결과를 보고 모델·분할·분류 기준을 다시 바꾸지 않았습니다. 기준 확률은 0.5입니다.

## 바꾼 내용

1. 데이터를 먼저 나누고 Pipeline 안에서 결측값 처리·인코딩을 학습하도록 수정했습니다.
2. 입력 전처리를 모델과 함께 저장해 API에서도 같은 변환을 사용합니다.
3. 문자 `None`(해당 사항 없음)을 보존합니다. 빈 셀만 결측값으로 처리합니다.
4. 기존 삭제 목록의 `name`은 실제 컬럼명 `full_name`과 달랐습니다. 이름을 제대로 제외했습니다.
5. `survival_probability`, `family_survival_rate`, 정답 `survived`, 빈 Unnamed 열을 입력에서 제외했습니다.
6. 범주형 변수에 대응하는 부스팅과 원핫 인코딩 로지스틱 회귀를 함께 비교했습니다.

## 85%가 어려운 이유와 한계

데이터의 `survival_probability`를 0.5 기준으로 분류해도 전체 행에서 정확도는 **76.81%**입니다.
해당 확률이 실제 조건부 생존 확률이고, 정답이 그 확률에 따라 독립적으로 생성되었다면,
`mean(max(p, 1-p))`로 계산되는 기대 최적 정확도는 **76.94%**입니다.
확률 구간별 실제 생존 비율도 해당 확률과 가깝습니다. 합성 확률 데이터일 가능성을 시사합니다.
다만 생성 코드를 제공받지 않았으므로 이 수치를 입증된 정확도 상한이라고 단정할 수 없습니다.
이 열은 진단에만 사용했고 학습·API 입력에는 넣지 않았습니다.

분할별 결측 분포도 특이합니다. 원본과 같은 seed=42에서 개발 데이터 80,000행의
`cabin_deck`, `emergency_response_time` 결측은 각각 0개인데, 테스트 20,000행에는
각각 18,000개(90%), 5,000개(25%)가 있습니다. 데이터 생성 또는 결측 주입 방식과
분할 난수의 관련성을 확인해야 합니다. 현재 검증 집합은 이 결측 분포 변화를 대표하지 못합니다.
다른 seed로 높은 점수가 나오는 결과만 고르지는 않았습니다.

85%가 필수라면 원본 데이터 생성 방식, 정답 생성 규칙, 허용 입력, 평가 기준을 교수님과 확인하는 것이 다음 단계입니다.
추가 특성이나 데이터 변경은 그 확인을 거쳐야 합니다. 정답 변경이나 정답 관련 열 투입으로 점수를 올리지 않았습니다.

## 입력·출력 및 예측 시점

입력은 23개 원본 특성으로, 정확한 형식은 학습 후 생성되는 `artifacts/schema.json` 및 `example_request.json`에 있습니다.
`family_size`, `fare_per_person`, `age_group` 등도 원본 값을 직접 받습니다.
파생 값 사이의 일관성은 자동 계산하지 않으므로 같은 시나리오에 맞춰 함께 수정해야 합니다.
생성 규칙을 모르는 `family_risk_score` 등은 원본 정의를 확인할 필요가 있습니다.

구명정 접근도, 비상 대응 시간, 대피 우선순위 등은 대피 상황을 알아야 입력할 수 있습니다.
따라서 이 API는 대피 상황 정보가 주어진 교육용 예측이며, 탑승 전에 알 수 있는 정보만 이용한 예측이 아닙니다.
출력은 `survived`(0/1), `label`, `survival_probability`(모델 추정 확률), 기준값, 모델명입니다.
API가 반환하는 확률은 데이터의 원본 확률 열을 그대로 돌려주는 값이 아닙니다.
