# 10주차: CI/CD 자동 배포 · 로그 기반 재학습 · 재배포 결과

## 1. CI/CD 자동 배포

9주차 CI/CD 가 팀 저장소에 남아 있지 않아(`.github/workflows` 없음, Actions 실행 0건) 새로 구성했습니다.

```
push ──> GitHub Actions CI ("test" 잡: 학습 -> scripts.validate -> pytest)
                   │ 성공
                   ▼
EC2 타이머(1분) ── 새 커밋 + CI 성공 확인 ──> git checkout -> pip install -> 학습 -> 재시작 -> /health 의 git_sha 확인
                                                                              └ 실패 시 이전 커밋으로 롤백
```

| 파일 | 역할 |
|---|---|
| `.github/workflows/adult-income-ci.yml` | CI. 모든 push/PR 에서 학습·검증·테스트, 지표를 Actions 요약에 출력 |
| `deploy/create_ec2.sh` | CloudShell 에서 EC2·보안그룹(8000) 생성, 학교 제공 역할 `yeonsung-ec2-ssm-cloudwatch-role` 사용 |
| `deploy/setup_ec2.sh` | EC2 최초 설정 (user-data): Python 3.11, venv, systemd 서비스·타이머 |
| `deploy/deploy.sh` | CD. CI 통과 커밋만 배포, 헬스체크 실패 시 롤백 |

**push 방식(GitHub → SSH) 대신 EC2 가 가져가는(pull) 방식으로 한 이유**
- GitHub Secrets 등록은 저장소 소유자만 가능 (팀원은 Write 권한)
- 수업 계정은 IAM 사용자/역할 생성이 막혀 있음 (`StudentGuardrails`) → Actions 에 AWS 키를 줄 수 없음
- SSH 포트를 열 필요가 없음 (8000 만 공개, 접속은 SSM)

**구성 중 고친 문제**
| 문제 | 원인 | 수정 |
|---|---|---|
| `iam:CreateRole` AccessDenied | 수업 계정 정책 | 학교 제공 인스턴스 프로파일 사용 |
| 배포가 한 번도 안 됨 (`deploy.sh: No such file`) | EC2 가 기본 브랜치(main)를 clone, 배포 스크립트는 작업 브랜치에만 있음 | 배포 브랜치로 clone |

배포 확인: push 후 약 2분 뒤 `/health` 의 `git_sha` 가 새 커밋으로 바뀜 (`10e57ca` → `1ff507c`).

## 2~3. 배포 서비스 테스트 → 로그 수집 → 전처리

- 배포 서비스에 holdout 1,000건 요청으로 성능 측정 (`scripts/evaluate_deployed.py`, `source="eval"` 로 표시해 재학습에서 제외)
- 가상 사용자 500명 (`scripts/simulate_users.py`): test 데이터의 traffic 절반에서 프로필 입력 → 실제 소득 피드백 → 약 절반은 👍/👎
- CloudShell 에서 `scripts/fetch_logs.py` 로 CloudWatch 로그 2,252건 수집 → `scripts/build_feedback_dataset.py` 로 전처리

전처리 결과와 분석은 [FEEDBACK_ANALYSIS.md](FEEDBACK_ANALYSIS.md) 참고. 요약:

| 단계 | 건수 |
|---|---|
| 전체 이벤트 (prediction 1,504 + feedback 748) | 2,252 |
| 성능 측정용 eval 요청 제외 | −1,000 |
| 정답(label) 있는 피드백 | 504 |
| 중복 제외 | −1 |
| **재학습 데이터** | **503** |

재학습 데이터 분석에서 본 것
- 배포 모델은 이 사용자들에게 **86.1%** 맞혔고, 오답 70건 중 41건이 "고소득 아닌데 고소득 예측", 29건이 "고소득 놓침"
- 예측 확률 **0.37~0.6 구간 정확도 50%**: 임계값 근처가 가장 불확실 → 이 구간 피드백이 재학습에 가장 유용
- 입력 분포(나이·학력·근무시간 평균)는 train 과 거의 같음 → 데이터 드리프트 없음
- 고소득 비율 27.6% (train 24.1%)

## 4~5. 재학습 · 재배포 · 전/후 비교

평가 기준: test 데이터를 traffic/holdout 으로 고정 분할 (`src/splits.py`). **holdout 은 재학습에 쓰이지 않으므로** 공정한 비교가 됩니다.

### 배포된 서비스에 같은 holdout 1,000건을 직접 요청해 측정 (`docs/deploy_eval/`)

| | 커밋 | 재학습 피드백 | 정확도 | F1 | >50K 재현율 | 응답 p50 |
|---|---|---|---|---|---|---|
| 재학습 전 | `10e57ca` | 0건 | **0.888** | **0.771** | 0.798 | 40ms |
| 재학습 후 | `1ff507c` | 503건 | 0.881 | 0.769 | **0.835** | 39ms |
| 변화 | | | −0.7%p | −0.003 | **+3.8%p** | |

### holdout 전체 8,141건 (학습 시 계산, `/model-info`)

| | 임계값 | 정확도 | F1 | >50K 재현율 |
|---|---|---|---|---|
| 재학습 전 | 0.37 | 0.8664 | 0.7296 | 0.7634 |
| 재학습 후 | 0.34 | 0.8605 | 0.7289 | **0.7941** |

### 변화가 어디서 왔나 (같은 임계값에서 비교)

| | AUC | 임계값 0.34 정확도 / 재현율 | 0.37 정확도 / 재현율 | 0.5 정확도 / 재현율 |
|---|---|---|---|---|
| 재학습 전 모델 | 0.9300 | 0.8595 / 0.7884 | 0.8664 / 0.7634 | 0.8769 / 0.6583 |
| 재학습 후 모델 | 0.9304 | 0.8605 / 0.7941 | 0.8656 / 0.7655 | 0.8786 / 0.6646 |

**결론**
- 개선된 점: **고소득(>50K) 사용자를 더 많이 찾아냄 (재현율 +3.1~3.8%p)**. 서비스 목적(연봉 협상 근거)상 "고소득 가능성 있는 사람을 놓치지 않기"가 중요해서 의미 있는 변화.
- 대가: 정확도 −0.6~0.7%p (고소득 아닌데 고소득으로 보는 경우 증가).
- 같은 임계값에서 비교하면 모델 자체는 거의 같음 (AUC +0.0004). **503건은 기존 32,537건의 1.5%이고 분포도 같아서** 모델이 크게 바뀌지 않았고, 변화는 대부분 재학습 때 F1 기준으로 다시 고른 **임계값(0.37 → 0.34)** 에서 나옴.

### 다음 개선 방향
- 피드백이 더 쌓이면 (특히 확률 0.37~0.6 구간) 가중치를 주어 재학습
- 임계값을 F1 대신 사용자 보상(reward) 기준으로 고르기 (강화학습 관점)
- 실제 사용자 피드백(`web`)은 3건뿐 → 팀원 테스트로 더 수집 필요
